# Setup and deployment

## 1. Local development

Install the .NET 10 SDK. Open `src/WeddingInvitation/WeddingInvitation.csproj` in Visual Studio, or run `dotnet run --project src/WeddingInvitation --urls http://localhost:5080` from the repository root. Open `http://localhost:5080`.

The app is standalone WebAssembly: no ASP.NET server is deployed. The development server is local only. Never send a localhost invitation link to guests.

The generic invitation is viewable without a guest ID. RSVP requires a valid link generated by the new backend. An empty `apiEndpoint` intentionally reports that RSVP is not configured rather than pretending to save.

## 2. Configure the new app

Edit **`src/WeddingInvitation/wwwroot/config.json`**. The former root configuration and legacy app files have been removed.

| Setting | Purpose |
| --- | --- |
| `coupleNames`, `welcomeText`, `blessingText` | Names and invitation copy |
| `invitationImage`, `saveTheDateImage` | HTTPS or relative artwork paths |
| `musicUrl`, `musicVolume` | Licensed HTTPS/relative audio source and volume from 0 to 1; blank disables music |
| `wedding` | Title, venue, address, map link, IANA venue timezone, start and end |
| `programme` | Ceremony event titles, descriptions and timestamps |
| `rsvp.closesAt` | Exclusive server cutoff, with explicit timezone offset |
| `rsvp.deadlineLabel` | Human-readable deadline in the venue timezone |
| `rsvp.maxAttending`, `rsvp.maxMembers` | Limits from 1 to 30; shared with Apps Script during setup |
| `rsvp.contactUrl` | Optional HTTPS contact link, such as a WhatsApp contact link; no private credentials |
| `calendar` | Stable ICS event ID and download filename for Add to calendar; existing Google/Outlook endpoint settings remain compatible |
| `sharing` | Manual WhatsApp URL and message template: `{family}`, `{couple}`, `{url}`, `{deadline}` |
| `apiEndpoint` | New Apps Script production deployment URL ending in `/exec` |

The artwork is stored directly in `src/WeddingInvitation/wwwroot/assets/` as `invitation.webp` and `save-the-date.webp`. Update these WebP files when replacing artwork; no PNG duplicate is retained. Text embedded in images is not generated from config: verify the names, date, and venue in the artwork yourself. Replace with artwork you own or have permission to use.

No music asset was supplied. Add a licensed audio file under `wwwroot/assets/` or a permitted HTTPS URL before enabling music. Opening the invitation attempts playback within a user gesture. A visible Play/Pause button remains available; device/browser restrictions or missing audio do not block RSVP.

### Timezone contract

- Wedding start: `2027-08-28T10:00:00+01:00` (10:00 UK / 09:00 UTC).
- Wedding end: `2027-08-28T18:00:00+01:00`.
- RSVP exclusive cutoff: `2027-08-09T00:00:00+01:00` (23:00 UTC on August 8).
- All visitors get the same remaining duration. Displayed dates use their browser's local timezone via `Intl.DateTimeFormat`.
- The Apps Script server clock decides whether a submission is permitted. Guests cannot extend the deadline by changing browser timezone or clock.
- Do not use a timezone-less date such as `2027-08-08T23:59` on the server.

Both the app and Apps Script reject timezone-less or invalid wedding, programme and RSVP timestamps. The cutoff must precede the wedding start, and the wedding end must follow the start. Shared test cases in `tests/configuration-cases.json` verify these rules in both implementations.

### Guest interaction and calendar

The journey is envelope → date reveal → invitation card → programme → wedding details → RSVP. Scratch the gold foil with a finger or pointer, press Enter/Space on it, or use **Reveal date**. Save the Date and Invitation share the same centered card styling. The date is revealed on the card without a popup. **Tap to enlarge** opens the invitation WebP in a full-screen viewer. Use **Zoom in** to read details, scroll or swipe through the artwork, and **Fit to screen** to restore the complete image. **Close** or Escape returns focus to the invitation card; the background page cannot be scrolled while the viewer is open.

Event details, directions and **Add to calendar** appear together on a full page immediately before RSVP. **Wedding details & RSVP** is a shortcut to that same page. RSVP keeps its deadline and household information, and going back does not discard form edits. Gold SVG illustrations are original decorative artwork, not photographs of the venue; their short animations begin on entering the viewport and respect reduced-motion preferences. The existing **Wedding celebrations & photo time** programme entry includes family photos and dancing at the unchanged 3:00 PM UK time.

**Get directions** opens Maps in a new tab with the confirmed destination **The Crystal Grand, 3 Bath Rd, Slough SL1 3UA, UK**. Guests choose their starting point and travel mode. The configured URL uses the complete address, not a verified place ID or entrance coordinate; verify the destination and entrance in Maps before sharing. Update `wedding.mapUrl` if the venue supplies an official directions link.

**Add to calendar** opens or downloads a standard `.ics` event containing the configured title, venue, start and end. The guest must confirm Add/Save in their calendar app. If the browser only downloads the file, open it from Downloads or import it into the preferred calendar. A website cannot silently save to a local calendar; support depends on the browser and installed app.

## 3. Publish to GitHub Pages

1. Follow [GIT-WORKFLOW.md](GIT-WORKFLOW.md) to push a review branch and merge into `main` after checks pass. If working from a downloaded ZIP, first establish the correct repository; local changes alone are not published.
2. In GitHub **Settings → Pages**, select **GitHub Actions** as the source.
3. Run **Build and deploy wedding invitation**. It runs offline tests, publishes Blazor and configures the repository-specific base path.
4. Wait for a successful deployment and open the displayed Pages URL. For the existing repository, this is `https://piranavie.github.io/Our-wedding/`.
5. Verify its `config.json` is the new config. The first deployment may leave `apiEndpoint` blank; this is needed to let Apps Script read the settings before its own deployment.

Only `publish/wwwroot` is uploaded, not tests, server code or editor settings. There is no client-side service worker, so an old offline app is not intentionally cached. Remove competing legacy Pages workflows if they exist in the remote repository.

Guest links use `#invite=...` on the root route, so GitHub Pages does not need a custom 404 router. The fragment is not sent to GitHub Pages in the HTTP request. It is read by the app and sent in POST bodies to Apps Script.

For another static host, publish with `dotnet publish src/WeddingInvitation -c Release -o publish` and set the `<base href>` in `publish/wwwroot/index.html` to that host's subdirectory. Serve over HTTPS.

## 4. Choose the workflow before creating anything

**Existing or uncertain setup:** follow [START-HERE.md, step 2](START-HERE.md#2-check-what-already-exists--do-not-reset-anything) first. Inventory the actual project's properties and inspect existing workbooks/backups. `diagnoseWeddingConfiguration()` is read-only and redacted; `checkWeddingSetup()` requires configuration and is not a discovery tool. Missing `APP_SETTINGS_JSON` only means the settings snapshot is missing/empty in that project, not that a workbook must be created. After confirming the project and published `SITE_URL`, `syncConfigurationFromWebsite()` restores only the snapshot without changing sheets or conversion records. It does not set `SPREADSHEET_ID`.

**Keep and convert the existing spreadsheet:** use the private conversion guide linked from START-HERE after ruling out a prior conversion/configured backend. Skip the new-workbook instructions below. Never clear `TRACKER_CONVERSION` or `SPREADSHEET_ID` to bypass guards; even a `completed` conversion record without `SPREADSHEET_ID` requires review.

### New workbook only — not the existing-tab conversion workflow

**Create a new Apps Script project rather than reusing a previously deployed legacy project.** Removing local legacy files does not delete old Google deployments or their automatic-send triggers. Disable any old sending triggers separately in the old project's Apps Script dashboard if they are no longer needed.

1. Create a new standalone Google Apps Script project while signed in as the wedding organizer.
2. Replace the empty `Code.gs` with **`google-apps-script/v2/Code.gs` only**.
3. Under Project Settings enable **Show appsscript.json manifest file**. Replace it with `google-apps-script/v2/appsscript.json`.
4. Under **Project Settings → Script properties**, add:
   - `SITE_URL` = the published invitation folder URL ending with `/`, e.g. `https://piranavie.github.io/Our-wedding/`.
5. Run `setupNewWeddingSpreadsheet()` from the editor. Review/authorize access to create a spreadsheet and fetch the public config.
6. Open the **Execution log** and copy the new spreadsheet URL. The function saves `SPREADSHEET_ID` and `APP_SETTINGS_JSON` in Script Properties. Do not copy the old spreadsheet ID into this project.
7. Confirm the new spreadsheet has `OUR WEDDING | RSVP DASHBOARD`, the nine-column `Guest List`, `RSVP`, and a hidden `RSVP Technical` tab.
8. Run `checkWeddingSetup()` to verify the configured sheet/schema/deadline. It does not submit an RSVP or validate browser access.

Setup refuses to run again once `SPREADSHEET_ID` exists, to prevent accidental duplication. It does not open, migrate or delete the old spreadsheet. Keep the old workbook private and untouched. Never clear existing data to resolve an error.

`APP_SETTINGS_JSON` is a server-side snapshot of the public config, avoiding a network fetch for every RSVP. After changing deadlines, limits, couple names or sharing templates, publish the config, run `syncConfigurationFromWebsite()`, then run `prepareInvitationLinks()` to refresh message links. Reopen invitation pages to load new settings.

## 5. Deploy the new public web app

1. **Deploy → New deployment → Web app**.
2. **Execute as: Me** (the owner of the new spreadsheet).
3. **Who has access: Anyone** (anonymous access, not merely anyone with a Google account).
4. Authorize and deploy. Copy the production URL ending in **`/exec`**, not `/dev` or a redirected `script.googleusercontent.com` URL.
5. Set `apiEndpoint` in **`src/WeddingInvitation/wwwroot/config.json`** to that exact URL.
6. Commit/upload the config and wait for GitHub Pages deployment to finish.
7. Open the endpoint in a signed-out/incognito window. It should return `ok: true`, service `Wedding Invitation API`, version `2`, method `POST`.

GET is a basic health signal, not proof that a POST saves correctly. Test valid-ID lookup and RSVP from the published app. After later code changes use **Deploy → Manage deployments → Edit → New version → Deploy** to retain the existing URL. If you create a new deployment instead, update the app config and republish.

Your organization may prohibit anonymous Apps Script apps. That restriction must be resolved by the owner; a frontend change cannot bypass it.

## 6. Add households and prepare invitation links

1. In **Guest List**, fill `Family side`, `Relationship type`, `Family Name`, and `Epected attendance` (exact spelling).
2. Leave **Invite ID blank for manually added new rows**. One row represents one household. Do not clear IDs assigned during import/conversion.
3. Use `Groom` or `Bride`. Expected counts must be whole numbers from 1 to the configured maximum.
4. Set **Invitation Status** to **Not sent** initially. This is separate from **RSVP Response**, which starts **Pending**.
5. Run `prepareInvitationLinks()` from the Apps Script editor. It validates rows, generates IDs for new households, stores technical data in the hidden tab and prepares column F. It **never sends messages**.
6. Copy **Invitation URL** into WhatsApp, email or another messenger and review the recipient before sending.
7. Only after sending, set **Invitation Status = Sent** manually. Generating or opening a link does not mean it was delivered.
8. Guest replies set **RSVP Response** to **Accepted** or **Declined** and update **RSVP No of People** automatically.

Do not use sequential IDs, row numbers, names or phone numbers as Invitation IDs. The helper uses random UUID-based 32-character IDs and checks for duplicates. Existing IDs are preserved when you regenerate links. Treat each ID as a password-like bearer credential. Do not post a real guest list, generated link CSV or screenshots containing IDs publicly.

To suspend a leaked invitation immediately, clear its Invitation URL and do not regenerate links until an organizer has reviewed revocation. Do not clear/change an existing Invite ID: it keys technical records and response history. Rotating active credentials requires a reviewed migration of the associated data.

The schema is fixed: don't rename or reorder system columns. Add new households below existing rows. Keep member data as valid JSON or let guests edit names in the app. Avoid manually editing RSVP/system columns while guests are responding.

### Import an existing Wedding Guest Tracker into a new workbook

For a tracker with `Family side`, `Relationship type`, `Family Name` (or `RSVP Family Name`), and `Epected attendance` (or `Expected attendance`) headers, install the optional **`google-apps-script/v2/ImportGuestTracker.gs`** alongside `Code.gs` in a **fresh** Apps Script project. Use the same manifest and `SITE_URL` setup described above. Do not run `setupNewWeddingSpreadsheet()` or add samples first.

1. Add Script Properties `SOURCE_SPREADSHEET_ID` (the source URL's spreadsheet ID) and `SOURCE_SHEET_ID` (the numeric `gid` for the guest tab). Keep identifiers and guest data out of public website configuration.
2. Run `previewGuestTrackerImport()`. It reads the source without editing it and logs totals plus source row numbers needing counts or phone review. It refreshes the script's configuration snapshot from the published website but creates no spreadsheet.
3. Run `createWeddingSpreadsheetFromTracker()`. It creates the standard **OUR WEDDING | RSVP DASHBOARD**, **Guest List**, and **RSVP** tabs in a new workbook, then imports all named households. The original workbook is unchanged. Open the new URL in the execution log.
4. Complete blank **Epected attendance** cells. Supplied valid counts are preserved; absent counts are not guessed. Imported phone/contact data, if present, is retained in hidden technical records, not extra Guest List columns.
5. Run `checkWeddingSetup()`, then `prepareInvitationLinks()` once counts and phones are ready. Finish the web-app deployment and `apiEndpoint` connection in section 5. Keep both workbooks private.

Blank-name rows are skipped. Missing side/relationship cells continuing an explicitly labeled Groom / Groom's friends block inherit that category until a different category or Bride section starts; review the preview's normalized row numbers. Other missing sides, invalid counts, duplicate required headers, or existing RSVP responses stop the import for review. Duplicate household names are retained as separate rows rather than merged.

This is a fresh invitation roster, not a migration of previously issued credentials or responses: old IDs, invitation URLs and delivery flags are not copied; imported rows start Pending / Not sent with new internal IDs and blank URLs. The hidden RSVP Technical tab retains their data. No messages are sent. Dashboard totals exclude imported rows until URLs are prepared. Do not use this workflow on an active tracker with responses; plan a separate response migration instead.

The creation helper refuses to run if `SPREADSHEET_ID` is already configured. Never clear that property to bypass the guard. If creation succeeds but a later write fails, retain the new workbook ID and inspect it before manual recovery; rerunning setup could otherwise duplicate data. The helper also refuses oversized imports exceeding the new tab's available rows.

### Back up and convert the existing tab in place

To keep the same spreadsheet and guest-tab `gid`, install **`ConvertGuestTracker.gs`**, **`ImportGuestTracker.gs`** and **`Code.gs`** together in a fresh owner-controlled Apps Script project, with the existing manifest. Set `SITE_URL`, `SOURCE_SPREADSHEET_ID` and `SOURCE_SHEET_ID` as above. Do not run either new-workbook creation function first.

1. Restrict spreadsheet sharing and disable legacy writers/sending triggers. Ask other editors to stop editing during conversion. Script locks do not block another project or a human editor.
2. Run `previewGuestTrackerConversion()` and review the summary. This checks required tab-name conflicts, source protections, counts, existing responses and previously issued invitation/delivery data. Resolve conflicts manually without deleting live records; the helper refuses to overwrite existing companion tabs.
3. Run `convertExistingGuestTracker()`. It copies the entire selected tab to **Guest backup <tab ID>**, verifies values/formulas against the source snapshot, and records `TRACKER_CONVERSION` recovery metadata before clearing the original tab. The original becomes **Guest List** with the same `gid` and exactly nine columns. It creates **RSVP**, hidden **RSVP Technical**, and **OUR WEDDING | RSVP DASHBOARD** in the same workbook. Other existing tabs remain, though formulas referencing the converted layout may need manual review. Workbook locale/timezone are left unchanged.
4. Keep the backup. Review households, complete blank counts and check phone country codes. After success `SPREADSHEET_ID` points to the existing workbook. Run `checkWeddingSetup()`, then `prepareInvitationLinks()` only once all required counts are valid. Deploy and connect the `/exec` endpoint as described in section 5.

This conversion refuses any existing `SPREADSHEET_ID` or `TRACKER_CONVERSION` property and never sends messages. Nonblank old IDs/URLs, delivery timestamps/sent flags or RSVP responses require a separate migration rather than resetting active invitations. Extra legacy columns are retained in the backup, not the new schema. Do not run this against an active responding guest list.

If any step fails after backup creation, stop: Google Sheets changes are not transactional. Keep `TRACKER_CONVERSION` and all backup/system tabs, inspect the recorded source/backup IDs, and recover manually before further actions. Do not clear the guard or rerun blindly. To retain the original `gid`, recovery must restore the source tab from the backup rather than delete it; review any partially created companion tabs and do not resume a backend until its schema is verified.

### Sample data

On a newly created empty Guest List, run `addSampleHouseholds()` to create two clearly marked samples with random IDs and no phone numbers. Alternatively import `v2/sample-guests.csv` into the empty Guest List and run `prepareInvitationLinks()`.

These samples are not real invitations and nothing is sent automatically. Remove only the sample records after verification. The sample dashboard starts at 2 invited households, 3 groom guests, 4 bride guests, 2 pending and 7 expected people.

## 7. RSVP behavior

A valid ID loads only that household. The current form shows Family name, Accept/Decline and Number attending when accepting. Unknown/missing IDs cannot register or modify households; the organizer must add them first.

Guests can change the family name, response and attending count (including children). Declining always saves zero attendees. Contact/member fields are no longer collected by the form. Existing stored names are preserved for backward compatibility and do not restrict a new minimal request's count. The backend still validates those fields if an older client explicitly submits them. Deploy the updated Apps Script code before using the simplified form with real guests.

Save updates the same Guest List row, appends a snapshot to the RSVP audit tab and refreshes dashboard formulas. A response is reported as successful only after the backend acknowledges it. Identical retries do not duplicate records; concurrent edits receive a reload prompt rather than silently overwriting newer data. A partial audit failure is repaired by an unchanged retry or the next valid save. Google Sheets is not a transactional database; monitor storage errors and keep workbook backups.

After cutoff, lookup still shows the saved household response, but the server rejects all updates. Contact the couple for offline changes.

## Troubleshooting “Failed to fetch” or storage failures

- Check the **published** `config.json`, not only the local copy. Confirm the correct new `/exec` URL.
- Confirm anonymous access in an incognito browser without Google login.
- Confirm the Apps Script endpoint returns **version 2**; legacy responses are incompatible.
- In browser Developer Tools → Network, check the POST destination and redirect response. A Google sign-in/HTML page means deployment/access needs fixing.
- POST uses `text/plain;charset=utf-8` and no custom authorization headers to avoid a CORS preflight. **Do not use `mode: no-cors`**; an opaque response cannot confirm a saved RSVP.
- In Apps Script **Executions**, inspect `Wedding API storage/configuration failure` details. Public responses deliberately do not expose sheet identifiers or internal errors.
- Run `checkWeddingSetup()`. Fix missing/renamed headers or authorization in the new workbook; never point v2 at the old schema.
- Wait for GitHub Actions to finish, then hard-refresh. Browser privacy extensions/network filtering can also block Google endpoints.
- Do not repeatedly send real test entries. Test using the clearly labeled sample household and verify both tabs.

## Privacy and service limits

The spreadsheet stays private. Anonymous users can only access a household if they possess its random ID; this is bearer-link access, not identity verification. Anyone with the link can edit that household until cutoff. No endpoint lists guests, searches by name, registers unknown guests or sends invitations.

The returned DTO excludes phone numbers and organizer metadata. No analytics are included; the HTML sets `no-referrer` and asks search engines not to index. Those settings are not authentication. Avoid third-party assets if unnecessary and do not store confidential information in config.

Apps Script/Google Sheets have free-tier quotas and are not abuse-proof. This design is for a private wedding guest list, not high-volume registration. Stronger authentication or abuse controls would require additional scope. Back up the workbook, limit sharing to organizers and delete personal data when no longer needed. Hidden audit columns are a convenience, not a security boundary.
