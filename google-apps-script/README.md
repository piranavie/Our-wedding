## Owner configuration required

The spreadsheet owner must deploy `Code.gs` as a Google Apps Script web app:

- Execute as the owner (an account with write access to this spreadsheet).
- Permit anonymous web-app requests so wedding guests do not need a Google login. This is endpoint access, NOT public access to the spreadsheet.
- Authorize the spreadsheet access requested by the deployment.
- Use the production deployment URL ending in `/exec`, not a test `/dev` URL or the spreadsheet viewing URL.
- Set `rsvpEndpoint` in the invitation's `config.json` to that HTTPS deployment URL and publish the updated configuration.

The static website cannot deploy or authorize this service. Keep `rsvpEndpoint` empty until the owner supplies the real deployment URL. Do not put Google passwords, access tokens, or service-account keys into public site files.

## Destination columns

The receiver uses columns A–E in the specified tab, in this exact order:

| Submitted At | Family Name | Attending | Guests | Request ID |
| --- | --- | --- | --- | --- |
| Server timestamp | Guest-entered name | Yes / No | Integer | Retry identifier |

An empty tab receives these headers on its first submission. If there is existing content, the headers must already match exactly. The receiver refuses mismatched headers rather than overwriting or appending into an unknown layout. Back up and review existing data before changing the tab; do not clear existing guest records just to configure this handler.

## Request contract

POST JSON using `Content-Type: text/plain;charset=utf-8` (the client already does this):

```json
{"name":"Thangasuthan Family","attending":true,"guests":3,"requestId":"0123456789abcdef0123456789abcdef"}
```

- Name: trimmed, nonempty, at most 120 characters.
- Attendance: a JSON boolean.
- Guests: integer 1–30 for acceptance, exactly 0 for a decline.
- Request ID: 32 lowercase hexadecimal characters, generated by the client. Identical retries in the same page session reuse the ID; reloading or changing the response creates a new submission.
- Success: `{"ok":true}` only after saving or finding the same request ID.
- Failure: `{"ok":false,"error":"..."}`. Apps Script ContentService responses may use HTTP 200 even for application errors; clients must check `ok`.

The handler validates inputs, uses a script lock to serialize writes, deduplicates retries, and escapes formula-like names. GET is a basic health response and never reads out RSVP records; it does not verify spreadsheet access.

This is a public submission endpoint, not an authenticated invitation system. A family name in a URL is personalization, not proof of identity. Anyone with the endpoint can submit valid data. For a small guest list, monitor submissions and service quotas; stronger anti-abuse controls require additional server-side verification. Keep the spreadsheet private and limit access to event organizers.

## Verification after deployment

Use the published invitation, not just the endpoint health response. Obtain approval before adding test entries to the real guest sheet.

1. Open a personalized link, complete the scratch activity, and navigate to RSVP.
2. Confirm that the family name is prefilled but editable.
3. With a clearly marked test name, accept for two guests; verify one correctly formatted row in the intended tab.
4. Decline using another test name; verify `No` and zero guests.
5. Verify an identical request ID cannot append a second row.
6. Verify malformed names, attendance values, guest counts, and IDs are rejected without adding rows.
7. Verify a failed network request shows an error instead of a success message; test cross-origin POST from the actual published site.
8. Remove only the explicitly created test records when finished.

Deployment restrictions, redirects, browser CORS behavior, and the spreadsheet schema must be checked with the real deployment before sending invitations to guests.

## Guest-list invitation sending process

Automatic delivery is implemented through the WhatsApp Cloud API and the `Guest List` tab.

### Required `Guest List` columns

- `Phone / WhatsApp` (existing guest phone column)
- `RSVP Family Name`

The script auto-adds these columns if missing: `Invite ID`, `Invitation URL`, `Invitation Status`, `Invitation Sent At`, `RSVP Response`, `RSVP No of People`, `RSVP Updated At`.
The script also maintains `Invitation sent` as `Yes` or `No`.

### Script properties (required)

Set these in Apps Script **Project Settings → Script properties**:

- `WHATSAPP_API_TOKEN` — permanent token for WhatsApp Cloud API
- `WHATSAPP_PHONE_NUMBER_ID` — Meta WhatsApp phone-number ID
- `INVITATION_BASE_URL` — published invitation URL (for example `https://piranavie.github.io/Our-wedding/index.html`)

Optional:

- `CONFIG_JSON_URL` — published `config.json` URL so this script can read `googleSheets` settings (sheet URL and column names)
- `RSVP_DEADLINE` — ISO date-time (for example `2027-08-08T23:59:00+01:00`) to block RSVP updates after deadline at server side

### How invitations are sent

Run Apps Script function `processInvitationsNow()`.

For automatic sending, use the sheet menu:

- **Wedding Invitations → Enable auto-send (every 15 min)**

This installs a time-driven trigger that runs `processInvitationsScheduled` every 15 minutes.
You can disable it from:

- **Wedding Invitations → Disable auto-send**

### Health check

Use **Wedding Invitations → Check system health** to verify:

- required script properties exist,
- optional properties status,
- auto-send trigger enabled/disabled,
- active sheet/tab/column mapping currently loaded by the script.

You can also run `checkInvitationSystemHealth()` directly from Apps Script editor and inspect the returned JSON.

For each guest-list row:

1. Skip rows where `Phone / WhatsApp` is blank.
2. Create/reuse `Invite ID`.
3. Build personalized URL with `family`, `phone`, and `invite` query parameters.
4. Send WhatsApp message automatically.
5. Update status columns (`Invitation Status`, `Invitation Sent At`, `Invitation URL`).
6. Update `Invitation sent` to `Yes` when delivered, `No` when sending fails.

Rows already marked `Sent`, or with `Invitation sent` = `Yes/true`, are skipped to prevent duplicates.

### RSVP synchronization back to guest row

When a guest submits RSVP from their personalized link, the script now:

- updates `RSVP Family Name` (corrected name from RSVP form),
- updates `RSVP Response` (`Accepted`/`Declined`),
- updates `RSVP No of People`,
- updates `RSVP Updated At`,

matched by `Invite ID` first, then `Phone / WhatsApp`.

Guests can update RSVP multiple times until the deadline. Each update writes the latest values to the guest row and appends a fresh RSVP log row.
